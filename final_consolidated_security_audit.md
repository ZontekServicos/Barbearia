# Final consolidated security audit

Audit date: 2026-10-01

Baseline: `0120b85` plus the reviewed working tree

Scope: React/Vite client, Express API, Prisma/PostgreSQL booking and payment changes,
administrative availability, public status page, and Caddy SPA routing.

## Findings

### SBP-001 — High — Resolved: cross-table booking/block race

`appointments` and `schedule_blocks` are separate tables, so the PostgreSQL
appointment exclusion constraint cannot arbitrate a concurrent booking and
administrative block. The reviewed implementation initially allowed both rows to
commit, leaving a hybrid state.

The fix uses the same transaction-scoped advisory lock for all writes on a shop
date and rechecks the other table after acquiring it:

- `server/src/modules/booking/appointments.service.ts:160-203`
- `server/src/modules/booking/schedule.service.ts:166-176`
- `server/src/modules/booking/schedule.service.ts:210-220`
- `server/src/modules/booking/schedule.service.ts:237-259`

The real PostgreSQL race test now requires one `201`, one `409`, and exactly one
persisted operation (`server/src/config/availability-admin.integration.test.ts`).

### SBP-002 — Low — Resolved: block input accepted an open object shape

The block body used a non-strict Zod object. The service already overwrote
`createdById` from the authenticated session, but silently accepting unknown
fields weakens the API contract and can hide attempted mass assignment.

`createBlockSchema` is now strict at
`server/src/modules/booking/booking.schemas.ts:117-126`. Integration coverage
verifies that injected authorship is rejected and that persisted authorship comes
from the ADMIN session.

### SBP-003 — Informational — Verified: administrative payment actions

The administrative router is protected centrally by authentication, active-account
validation, and `requireRole("ADMIN")` at
`server/src/modules/admin/admin.routes.ts:26`. Payment settlement accepts a strict
enum-only body at `server/src/modules/booking/booking.schemas.ts:288-290` and the
service performs payment and appointment transitions in one transaction.
Unauthenticated and CUSTOMER calls are covered by integration tests as `401` and
`403`.

### SBP-004 — Informational — Verified: public data minimization

The public availability response contains clock/instant values and `available`
only. Appointment IDs, block IDs, reasons, customer data, and service/customer PII
remain in the ADMIN response. Public request tokens are stored server-side only as
digests and provide access to one request rather than a listing endpoint.

The browser keeps that opaque request capability in `localStorage` so a customer
can reopen the status link. This is an intentional product requirement; it makes
XSS prevention material. The only HTML sink found is the QR SVG generated by the
server's QR library, not user-supplied markup.

### SBP-005 — Informational — Verified: HTTP and session controls

The API configures an explicit proxy hop count, Helmet, an exact CORS allow-list,
a 100 KB JSON limit, global rate limiting, narrow refresh-cookie scope, and a
custom-header CSRF check for cookie-authenticated `/auth` mutations
(`server/src/app.ts:25-78`). ADMIN APIs use the bearer access token and current
database role/status checks. No unsafe raw SQL API, command execution from request
data, open redirect, or untrusted URL fetch was found in the reviewed changes.

## Dependency and secret checks

- `pnpm audit --prod` returned no known vulnerabilities for both packages.
- Diff review found no committed credential, private key, database password, or
  production token.
- `.env.example` documents names and constraints only; Pix receiver ownership is
  explicitly described as operator-configured and not bank-validated.

## Open security findings

No unresolved critical, high, medium, or low finding remains in the reviewed
scope. Deployment behavior at Railway remains an operational verification item:
the repository cannot prove that the frontend service actually consumes the
versioned `Caddyfile`.
